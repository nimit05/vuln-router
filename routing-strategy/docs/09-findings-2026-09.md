## 1. The verifier-gated cascade is closed, at full coverage

`ROUTER_V2_PERCASE.md` §2.1 rejected the cascade on a few hand-picked variants.
This re-ran it over **all 12 ordered model pairs × 3 bug types**.

```
python3 LLMDFA/scripts/cascade_allpairs.py
```

A cascade sends every case to the small model, runs Z3, and re-runs only the
Z3-rejected cases on the large model.

### Z3 rejection rate, per model and bug type

| model | bug | n | Z3 rejects |
|---|---|---|---|
| Phi-4-mini | dbz | 292 | **83.9%** |
| Mistral-Nemo | dbz | 293 | **92.8%** |
| granite-8b | dbz | 300 | **91.3%** |
| Qwen-7B | dbz | 1851 | 31.8% |
| Phi-4-mini | xss | 666 | 14.3% |
| Qwen-7B | xss | 666 | **0.0%** |
| all four | osci | 444 | 6–10% |

### Result: 1 non-degenerate win out of 12 pairs, and it is noise

The single survivor is `xss Mistral→granite`: **+0.005 F1** over Mistral alone
at **1.02× its cost**, on the bug type where every model already sits at
0.95–0.97 F1 and E17 measures a 0.7-point precision spread. That is within
noise, on the corpus where routing is known not to matter.

Everything else fails in one of two ways:

- **Rejection too rare → the gate never fires.** Qwen on xss rejects 0.0%, so
  the "cascade" is Qwen alone and never reaches the large model's 0.967.
- **Rejection too common → you buy both models.** On dbz, `Phi→Nemo` escalates
  241 of 286 cases: 13,137 s (Phi on all) + 19,007 s (Nemo on the rejects) =
  **32,144 s**, against 20,687 s for Nemo alone. **1.55× the cost.**

And on dbz the cascade F1 (0.552) lands **below both** models (Phi 0.604, Nemo
0.568). Z3 is firing on cases where the small model was *right*.

### Mechanism: `z3_fail` measures the model, not the case

Same 286 dbz cases, same solver, four models:

| model | rejects |
|---|---|
| Qwen-7B | 31.8% |
| Phi-4-mini | 83.9% |
| granite-8b | 91.3% |
| Mistral-Nemo | 92.8% |

If `z3_fail` tracked *case difficulty*, all four would reject roughly the same
cases. A 61-point spread says it tracks **"can this model emit syntactically
valid Z3"** — a property of the model, not of the program.

**One line for the paper:** *the verifier checks the model's output format, not
the case's hardness, so it cannot serve as a difficulty signal.* This sits
alongside the shuffled-oracle result: both say per-case difficulty is not
observable here, one from features, one from verifiers.

## 2. Three corrections to the pre-flight doctrine

### 2.1 The shuffled oracle must not gate — it rejects DBZ

`PROGRESS.md` E17 states step 2 as *"test against the shuffled-oracle null; if
the real oracle is at or below the shuffle, stop."* **That criterion rejects
the one corpus where routing works.**

| corpus | real oracle | shuffled oracle | rule actually works? |
|---|---|---|---|
| DBZ (in-sample) | 0.796 | 0.916 | **yes, z +5.9** |
| off815 | 0.805 | 0.940 | **yes, z +5.5** |

§9 already recorded that the oracle sits below the shuffle *in every condition*,
off815 included — so as written, step 2 rejects everything.

The two nulls answer different questions:

- **Shuffled oracle** — is there headroom in *per-case model choice*? No, anywhere.
- **Matched-count random split** — does *this rule* carry information? Yes, on DBZ.

The rule wins while the oracle gap is fake because **it is not picking the best
model per case.** It exploits a distribution-level crossover: the small model
emits ~half the false alarms on branchy programs (1.42 vs 2.27 FP/case at
`n_if ≥ 12`). That is a property of a *group* of programs.

**The shuffled oracle stays as a reporting rule** — never quote an oracle as
headroom or as a target — **not as a gate.**

### 2.2 Gate 1 (dispersion) is a screen, not a gate

E17 step 1 asks whether the models disperse on the target metric. That compares
models **marginally**. Routing needs them to differ **conditionally**.

Demonstrated on synthetic data: a corpus where `m1` is good on high `k` and
`m2` is good on low `k` — a perfect routing case — has **identical marginal
precision** (2.0 points apart, below any sane floor) and would be rejected by
step 1. Gate 2 scores the same corpus at **z +11.5**.

So step 1 only decides when there is no candidate feature to test. Where a
feature exists, **step 2 subsumes step 1**: gate 2 alone still rejects XSS
(z −1.7) and OSCI (z +0.5) correctly.

Step 1 is also confounded when models sit at different operating points. On
PrimeVul recall spans **3.8% → 88.9%**, so precision differences are the
precision/recall trade-off, not skill.

### 2.3 The routing *direction* must be fixed before the run

On IRIS, with prompt length (`in_tokens`) as the feature and the same relative
cut and the same 923 selected cases:

| direction | F1 | z |
|---|---|---|
| long prompts → small model | 0.192 | **−5.8** |
| long prompts → large model | 0.300 | **+7.8** |

Swapping which model is called "small" turns a NO-GO into a GO. Anyone can try
both and report the winner. The LLMDFA work did this correctly — the rule was
frozen before jobs 2372 / 2417 ran — but nothing in the method *enforced* it.
`router.py` now always prints both directions with that warning attached.

A strongly negative z is itself informative: it means the feature carries
signal pointed the other way. That is a hypothesis for held-out data, never a
result to claim from the same table.

## 4. Defects found by cross-dataset testing

| # | found on | defect |
|---|---|---|
| 1 | Juliet tree | `[a-g]$` suffix strip invented phantom programs (`AbstractTestCase` → `AbstractTestCas`). Only the Juliet `_\d+[a-g]` multi-part form should collapse. |
| 2 | Juliet tree | `route` echoed its raw return value through `sys.exit`. |
| 3 | LLMDFA logs | `export` filtered on the log *filename*; the bug type is in the file header. |
| 4 | **PrimeVul** | A model with no positive predictions was reported at **0% precision** rather than undefined. That fake 0 set the floor of the spread: **24.1 → 8.9 points**, turning a NO-GO into a PASS. |
| 5 | **PrimeVul** | Precision estimated from a handful of predictions counted as real — `deepseek-6.7b` predicts positive **4 times in 5,820**. Now `--min-predictions` (default 30). |
| 6 | **PrimeVul** | Precision spread confounded by operating point. Now warns. |
| 7 | **IRIS** | Gate 2 required Java source, so it could not run off the Juliet corpora at all. Now `--feature <numeric jsonl field>`. |
| 8 | **IRIS** | Gate 2 permitted post-hoc direction selection (§2.3). |
| 9 | synthetic | Gate 1 as a hard stop rejects genuinely routable corpora (§2.2). |

Edge cases verified: single model, empty input, non-overlapping case sets,
missing `sec`, constant feature, non-numeric feature, degenerate cut,
JSON-array input.

Defects 4, 8 and 9 are the ones that change conclusions. 4 and 9 would have
produced a wrong verdict; 8 would have permitted an unreplicable claim.

## 5. Field positioning (for related work)

Searched 2026-09-19. Useful for placing the project, not a project result.

- **LLM-as-detector dominates by count.** An SLR of 263 studies (Jan 2020 – Nov
  2025) finds **74.1% formulate the task as binary classification**; an
  independent ML4VD analysis puts **88%** of state-of-the-art techniques at
  function-level binary classification; a 208-study review finds **91.3%**
  detection versus 11.1% repair and 5.3% explanation. ~83% operate on isolated
  code rather than inside a pipeline.
- **LLM-as-verifier dominates the top-venue hybrids.** Where a classical
  analyzer supplies candidates, the LLM is most often the alert-triage stage —
  IRIS, ZeroFalse, AdaTaint, the Datadog deployment, industrial Linux-kernel
  triage.
- **The 2026 agentic line moves verification *away* from the LLM.** Big Sleep,
  XBOW, Revelio and the CyberGym / SEC-bench Pro / ZeroDayBench benchmarks put
  the LLM in the explorer role and hand verification to a deterministic oracle
  (a crash, a sanitizer report, a working exploit).
- **Defensible framing:** the LLM is assigned whichever stage needs contextual
  judgement a sound analyzer cannot express — triage, spec inference, or
  exploration. "Verification" is not a fixed role, and an LLM triager does not
  verify in the soundness sense.

This project's contribution sits against the first bullet: the routing
literature (RouteLLM, GraphRouter) is built on per-instance difficulty
prediction, and this project measures that it does not hold in program
analysis.
