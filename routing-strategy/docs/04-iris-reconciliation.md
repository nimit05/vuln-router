# Reconciling our candidate set with IRIS's

Status: **gate passed**, 16/16 projects, exact on paths, true positives and recall.

Our router replaces IRIS's posthoc LLM filter, so both stages must consume the
identical alert stream. Until they did, no number we produced belonged in the
same table as theirs. This records what was wrong, what it turned out to be, and
what the corrected set looks like.

## What was wrong

The old extractor emitted one row per SARIF **result**, kept only `codeFlows[0]`,
and deduplicated across query files. IRIS counts something else entirely.

Their `EvaluationPipeline.evaluate_sarif_result` does three things we did not:

1. **Every codeFlow is a path.** `iter_code_flows` walks `runs[0]["results"]` and
   yields every `codeFlow` of every result. One result routinely carries several.
2. **A filter runs first.** `ignore_code_flow` drops a flow whose FIRST or LAST
   step message mentions `toString` or `println` — formatting hops, not taint.
   Across the 16 projects this removes 103 flows.
3. **True positives are resolved at method granularity, not by line range.**
   Each step is mapped to its enclosing `file:class:method` using CodeQL's own
   `fetch_class_locs` / `fetch_func_locs` tables, and that set is intersected
   with the fixed methods from `fix_info.csv` (test files dropped). Comparing a
   SARIF line against `method_start`/`method_end` — what we did — is a different
   test, because the fix line numbers refer to the patched tree while the
   database is built at the buggy tag.

## The part that was not our bug

Reconciling against the cached `output/<proj>/v15_full17/cwe-*wLLM-final/
results.json` still failed on 6 projects after all three fixes. It was not our
extractor.

Running **IRIS's own evaluator over the current SARIFs** reproduces our numbers
exactly on all 16 projects — ff4j 1413 paths / 181 TP, ESAPI 198 / 99 — while the
cached JSON claims 1229 / 180 and 165 / 79. The caches describe an earlier,
smaller query run that a later re-run never refreshed.

This mattered more than a bookkeeping slip. Had the cached numbers been treated
as ground truth, a correct extractor would have been "fixed" until it matched
them, and the IRIS baseline rows of the final table would have been computed
from a different alert set than the router rows.

So truth is regenerated by `b0_iris_truth.py`, which calls their evaluator on
today's files. The cached values are carried along as `stale_*` fields.

## The corrected set

|  | old (per alert) | new (per path) |
|---|---|---|
| candidates | 2,520 | 2,259 |
| true positives | 98 (3.89%) | 344 (15.23%) |
| projects contributing | 5 | 14 (16 scored) |
| largest project's share | rocketmq 66% | ff4j 63% |

`apache__rocketmq` is gone. It has 1,620 alerts on disk but no
`cwe-094wLLM-final/results.json`, so IRIS never scored it; including it made it
two thirds of the pool and pushed the CWE mix to 89.6% CWE-94.

Two projects are scored with zero paths (`json-sanitizer`, `perfecto-plugin`).
They stay in the denominator: AvgF1 is a mean over ALL projects, so dropping
them would inflate every row.

## What this fixes about the comparison

The unfiltered path set — IRIS's alerts with no LLM filter at all — already
scores:

| Configuration | #Det | rate% | AvgFDR% | AvgF1 |
|---|---|---|---|---|
| no filter (all 2,259 paths) | 10/16 | 62.50 | 82.12 | 0.212 |
| paper: IRIS + DeepSeekCoder-7B | 10/16 | 62.50 | 81.31 | 0.215 |
| paper: IRIS + GPT-4 | 10/16 | 62.50 | 65.69 | 0.366 |
| per-path oracle (upper bound) | 10/16 | 62.50 | 9.09 | 0.625 |

Every configuration detects the same 10 projects, because 10 is how many contain
a true-positive path at all. **Detection is saturated; the entire comparison is
about false-discovery rate.** A router cannot find a vulnerability the alert set
does not contain — it can only decide which alerts to keep.

That reframes the deliverable. The question is not "does routing detect more"
but "how far down the 82% → 9% FDR range can a router get, and does it beat
GPT-4's 66%".

## A limit on the CWE-node extension

Each project carries exactly one CVE, and IRIS runs only that project's CWE
query. So `query_cwe == gold_cwe` on every row, and CWE is a function of project:

| CWE | projects | paths |
|---|---|---|
| CWE-94 | 3 | 1,669 |
| CWE-22 | 5 | 309 |
| CWE-79 | 4 | 265 |
| CWE-78 | 2 | 16 |

A CWE node can therefore shift routing between projects but never between paths
within one. Under leave-one-project-out it is close to a project-identity
feature. Worth stating plainly in the write-up, since the CWE hierarchy is the
user's extension to GraphRouter and this bounds what it can contribute.

## Pipeline

```
b0_iris_truth.py     IRIS's evaluator over current SARIFs  -> iris_truth.json
b1_extract_paths.py  one row per surviving codeFlow        -> paths.jsonl
b2_label_paths.py    TP at file:class:method               -> paths_labelled.jsonl
b1_validate.py       THE GATE: must match iris_truth.json  -> exit 0
b3_slice.py          slice along the path                  -> slices.jsonl
b3b_make_units.py    probe units (sliceable only)          -> units_paths.jsonl
b6  (csecluster)     5 models x 2,257 units                -> probe_out/*.jsonl
b6b_router_data.py   GraphRouter's router_data.csv         -> router_data.csv
c1_score_table.py    keep/drop -> IRIS metrics             -> RESULTS_TABLE.md
```

`b1_validate.py` exits non-zero unless every project matches. Treat that as a
hard stop.
